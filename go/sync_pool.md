# sync.Pool

Про sync.Pool обычно пишут в контексте оптимизации. Меньше аллокаций, ниже
давление на GC, быстрее обработка. Звучит как бесплатный буст, поэтому
разработчики начинают пулить всё подряд. А потом бенчмарки показывают, что стало
хуже.

`sync.Pool` это один из самых неправильно понимаемых типов в стандартной
библиотеке. Выглядит как пул объектов, им и является, но с одной гарантией,
которая удивляет: `GC` может выселить всё содержимое пула в любой момент, без
предупреждения.

`sync.Pool` реально нужен для одного конкретного сценария: снизить давление
аллокаций для короткоживущих переиспользуемых объектов: bytes.Buffer, структуры
протокольных сообщений, временные срезы.

```go
var bufPool = sync.Pool{
    New: func() any {
        return new(bytes.Buffer)
    },
}

func processRequest(data []byte) []byte {
    buf := bufPool.Get().(*bytes.Buffer)
    buf.Reset() // обязательно: сбрасываем перед использованием
    defer bufPool.Put(buf)

    buf.Write(data)
    return buf.Bytes()
}
```

## Главные ошибки

### Reset

Пул переиспользует объект, но не его содержимое. Всё, что записал предыдущий
пользователь, никуда не делось. Всегда сбрасывать состояние перед работой с
полученным объектом.

### Put

Использовать объект после Put. Как только вызван Put - объект принадлежит пулу.
Обращение к `buf.Bytes()` после возврата - это гонка данных, которая просто ещё
не выстрелила.

### Маленькие объекты

Пулить структуру из трёх `int` - хуже, чем просто создать новую. У пула есть
собственные накладные расходы:

1. упаковка в `any` (interface boxing);
2. `type assertion`при каждом Get;
3. атомарные операции на P-локальном кеше;

Для маленьких объектов эти расходы перевешивают стоимость обычного `new`.

### Долгоживущие объекты

`sync.Pool` спроектирован для вещей, которые вы берёте, используете и
возвращаете в рамках одной операции. Взяли буфер, записали ответ, вернули. Если
объект живёт между запросами или хранит состояние на протяжении сессии, пул не
нужен. Просто храните ссылку.

### Буферы переменного размера

Допустим, есть пул `[]byte`. Большинство буферов занимают 1KB, но изредка
некоторые вырастают до 10MB. После возврата в пул эти 10MB остаются
закреплёнными в памяти до следующего цикла `GC`. Под нагрузкой таких раздутых
буферов накапливается много, и потребление памяти растёт непредсказуемо.

#### Решение

Ограничивать размер того, что возвращается в пул:

```go
defer func() {
    if buf.Cap() < 64*1024 {
        bufPool.Put(buf)
    }
}()
```

Буферы крупнее порога просто отпускаются в `GC`. Если размеры сильно разнятся,
можно завести отдельный `sync.Pool` для каждого класса размеров.

## Как понять, что пул вредит

Запустить бенчмарк с -benchmem и сравнить версии с пулом и без:

```bash
BenchmarkHandler-8 500000 2400 ns/op 1024 B/op 3 allocs/op
BenchmarkHandlerPooled-8 800000 1500 ns/op 48 B/op 1 allocs/op
```

Такой результат означает, что пул работает. Но если ns/op вырос, а allocs/op
почти не изменился, пул обходится дороже, чем аллокация, и не стоит его
использовать.

В проде настоящий эффект пула виден через метрики `GC`: частоту запусков и
длительность пауз (`runtime.ReadMemStats`, `pprof`). Если пул не снижает эти
показатели, он занимает место в коде без пользы.

`sync.Pool` не стоит применять по умолчанию. Сначала профилирование, поиск
аллокаций, которые реально влияют на производительность, и только потом проба
пула. Замерь результата. Если улучшения нет, откат. Большей части кода пул не
нужен.
