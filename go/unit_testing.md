# Best practices unit-тестов в Go

## Table-driven тесты

Это идиоматический подход в Go. Все сценарии описываются в срезе структур и
прогоняются в цикле через `t.Run`. Добавить новый кейс - одна строка.

```go
tests := []struct {
    name     string
    input    int
    expected int
    wantErr  bool
}{
    {"positive", 5, 25, false},
    {"zero", 0, 0, false},
    {"negative", -1, 0, true},
}

for _, tt := range tests {
    t.Run(tt.name, func(t *testing.T) {
        result, err := Square(tt.input)
        if (err != nil) != tt.wantErr {
            t.Errorf("error = %v, wantErr %v", err, tt.wantErr)
        }
        if result != tt.expected {
            t.Errorf("got %d, want %d", result, tt.expected)
        }
    })
}
```

## Подтесты с помощью t.Run

Подтесты позволяют запускать конкретный сценарий по имени. Это экономит время
при отладке, когда не нужно гонять весь набор:

```bash
go test -run TestSquare/negative
```

## Хелперы через t.Helper()

Без `t.Helper()` стек ошибки укажет на строку внутри хелпера. С ним — на строку
вызова в тесте:

```go
func assertEqual(t *testing.T, got, want int) {
    t.Helper()
    if got != want {
        t.Errorf("got %d, want %d", got, want)
    }
}
```

## Map вместо Slice

Лучше заменить `[]struct{...}` на `map[string]struct{...}`, где ключ мапы - это
name теста. Почему? Итерация по мапам в Go рандомизирована. Это значит, что при
каждом запуске тест-кейсы будут выполняться в разном порядке. Это отличный
способ убедиться, что тесты не зависят друг от друга, не разделяют глобальное
состояние.

## t.Parallel() для скорости

`t.Parallel()` говорит Go-тесту: «Этот тест можно запускать одновременно с
другими параллельными тестами». Это ускоряет выполнение тестов, особенно если
они делают I/O (сеть, диск, БД) или спят. Добавить `t.Parallel()` первой строкой
внутри `t.Run`.

## Мок зависимостей через интерфейсы

Определяется интерфейс. В проде подставляется реальная реализация, в тестах —
мок:

```go
type Storage interface {
    Get(id int) (*Item, error)
}

type MockStorage struct {
    items map[int]*Item
}

func (m *MockStorage) Get(id int) (*Item, error) {
    if item, ok := m.items[id]; ok {
        return item, nil
    }
    return nil, errors.New("not found")
}
```

## Тестирование поведения, а не реализации

Если тест ломается при рефакторинге внутренней логики без изменения внешнего
контракта - это плохой тест. Стоит начинать с покрытия экспортируемых функций.
Один тест проверяет одну вещь.

## Тесты должны иметь понятные имена

Имя теста должно описывать сценарий и ожидаемый результат. При падении вы должны
понять, что сломалось, не открывая код.

## Запуск тестов с флагом -race

Детектор гонок ловит проблемы конкурентного доступа, которые почти невозможно
найти вручную.

```bash
go test -race ./...
```

## Нет смысла в 100% покрытия

Высокий процент не гарантирует отсутствие багов. Нужно покрывать критическую
логику и граничные случаи. Качество тестов важнее количества.

## TestMain для дорогого setup

Если подготовка окружения занимает время, вынесите её в TestMain. Она
запускается один раз на весь пакет, а не перед каждым тестом:

```go
func TestMain(m *testing.M) {
    setup()
    code := m.Run()
    teardown()
    os.Exit(code)
}
```

## Выбор инструмента под задачу

- стандартный `testing` для большинства случаев;
- `testify` добавляет удобные ассерты и моки;
- `httptest` закрывает тестирование HTTP-хендлеров;
- `testcontainers-go` помогает с интеграционными тестами через Docker;
